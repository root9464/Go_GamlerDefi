# Документация: Архитектура, структура и принципы проектирования

## Общая структура проекта

```
- src
  - config
  - core
    - head
      - index.go
      - init_module.go
      - main.go
  - database
    - mongo
    - postgres
    - redis
    - database.go
  - modules
    - test_module
      - adapters
      - controller
      - dto
      - helpers
      - model
      - repository
      - service
      - module.go
      - test
  - packages
  - submodules
```

## Базовые слои

### helpers

> Вспомогательные функции для мутирования и подготовки данных.  
> Примеры: сериализация/десериализация, преобразование структур (JSON → struct), нормализация.  
> **Правило:** здесь не должно быть бизнес-логики, только техничка.

### models

> Доменные модели БД (ORM/SQL схемы, raw-entity).  
> Прямое отражение таблиц или документов в базе.  
> **Правило:** не использовать эти модели в API напрямую (для этого `adapters`).

### utils

> Мелкие чистые функции общего назначения.  
> Примеры: парсинг строки в дату, работа с UUID, math-хелперы.  
> **Правило:** не зависят от домена, можно копировать в другой проект.

### adapters

> Конвертация данных между слоями:

- `model` ↔ DTO (API).
- `event payload` ↔ internal struct.  
  Слой маппинга, здесь нет бизнес-логики.

## Остальные слои

### domain

> Чистые доменные сущности и агрегаты.

- Хранят только бизнес-инварианты и поведение.
- Не зависят от базы, фреймворков, транспорта.  
  **Примеры:** `User`, `Order`, методы валидации и инвариантов.

### entity

> Конкретные доменные **сущности** с идентичностью.

- Отражают реальные бизнес-объекты.
- Содержат методы, которые изменяют их состояние.
- Живут дольше, чем отдельные сценарии (usecase).  
  **Пример:** `Order.Pay()`, `User.Activate()`.

### usecase

> Реализация конкретных бизнес-сценариев.

- Оркеструет вызовы сущностей, сервисов и репозиториев.
- Гарантирует целостность и корректность выполнения.  
  **Примеры:** `CreateOrder`, `TransferMoney`, `ActivateUser`.

### service

> Компоненты бизнес-логики, которые можно переиспользовать.

- Инкапсулируют работу с доменом или внешними системами.
- Вызываются из `usecase`.  
  **Примеры:** `PaymentService`, `NotificationService`.

### infrastructure

> Реализации внешних интерфейсов, объявленных в `domain` или `application`.

- Репозитории (Postgres, Redis, S3).
- Event-bus (Kafka/NATS).
- HTTP/gRPC клиенты.  
  **Правило:** не содержат бизнес-логики, только адаптеры под конкретные технологии.

### interfaces

> Транспортный слой и внешние точки входа/выхода.

- REST/gRPC handlers.
- GraphQL резолверы.
- Консьюмеры событий (event consumers).  
  **Задача:** принять запрос, преобразовать данные (через `adapters`), вызвать `usecase`, вернуть ответ.

### events

> Определения доменных и интеграционных событий.

- Событийные payload-структуры.
- Топики/чаннелы (Kafka topic names, NATS subjects).  
  **Примеры:** `UserCreated`, `OrderPaid`.

### bridgets

> Необязательный слой для нормализации несовместимых архитектур между модулями

- Нормализация
- Служит как вспомогательный слой для того чтобы использовать что то из 1 архитектуры если оно несовместимо

## Правила структуры и нейминга (обязательные, без компромиссов):

### 1. Каждый слой = один пакет

> Каждый слой = один пакет. Внутри папки слоя запрещено делать подпапки с отдельными пакетами. Допускается только деление логики по файлам.
> Пример:  
> modules/test_module/controllers/http.go  
> modules/test_module/controllers/ws.go Оба файла принадлежат пакету test_controllers.

### Файл, содержащий фабрику инициализации, интерфейсы и точку входа для слоя, обязан называться как сам слой.

> Примеры: Для слоя controllers: controllers.go. Для слоя service: service.go. Для слоя repository: repository.go.

### Имя пакета всегда начинается с префикса модуля.

> Формат: <module>\_<layer>. Примеры: Модуль test, слой моделей → пакет test_models. Модуль test, слой сервисов → пакет test_service. Модуль
> billing, слой репозиториев → пакет billing_repository.

### Нейминг файлов всегда в нижнем регистре и в snake_case

> Примеры: user_dto.go order_repository.go payment_service.go controllers.go (если это фабрика слоя или корневой файл)

### В одном файле не должно быть логики из разных смысловых блоков.

> DTO → отдельный файл с суффиксом \_dto.go. Репозиторий конкретной сущности → отдельный файл с суффиксом \_repository.go. Сервис → отдельный
> файл с суффиксом \_service.go.

### Внутри слоя допустимы только файлы, относящиеся к этому слою.

> В repository запрещено хранить DTO. В service запрещено хранить модели БД. В controllers запрещено хранить бизнес-логику.

## Архитектрные правила

### Краткое правило

> Каждый модуль может иметь любую архитектуру (clean, DDD, event-driven и т.д.), но структура папок и правила нейминга обязательны. Внешние
> зависимости модуля обращаются только к экспортируемым абстракциям (интерфейсам). Конкретные реализации инжектятся через фабрики при сборке
> приложения. Все публичные методы слоёв принимают context.Context первым аргументом.

### Нейминг и правила фабрик/интерфейсов (жёстко)

1. Интерфейс слоя всегда именуется I<Prefix>, где <Prefix> = имя модуля + смысл слоя. Примеры: IReferralRepository, IReferralService, IReferralBridgets.
2. Фабрика слоя всегда именуется New<Prefix> и обязана возвращать интерфейс, не структуру. Примеры: NewReferralRepository(...) IReferralRepository; NewReferralService(...) IReferralService.
3. Категорически запрещено, чтобы фабрика публично возвращала конкретный тип (\*ReferralRepository или &ReferralRepository). Если нужно — фабрика возвращает (I..., error) только в случае, когда создание может ошибаться; иначе (I...) допустимо.
4. Конкретная структура реализации должна быть unexported (например referralRepository) — чтобы нельзя было импортировать и ссылаться на конкретную реализацию вне пакета. Экспортировать только интерфейс и фабрику.
5. Файлы: factory.go — фабрика, interface.go — интерфейс(ы), impl.go — реализация(и). Это упрощает ревью и поиск.
6. Если создание может провалиться (подключение к внешнему ресурсу, валидация конфигурации) — сигнатура фабрики должна быть NewX(...) (IX, error).
7. Если фабрика всегда успешна (простая в памяти реализация) — NewX(...) IX допустимо.
8. Фабрика не должна выполнять бизнес-логику. Инициализация инфраструктуры и валидация аргументов — ок.
9. Интерфейсы минимальны и ориентированы на поведение (interface segregation). Предпочтение композиции маленьких интерфейсов.

### Bridgets (обязательное объяснение)

1. Bridgets — опциональный слой-адаптер внутри модуля для нормализации несовместимых архитектур (например clean vs event-driven). Папка: modules/<module>/bridgets.
2. Назначение bridgets: трансформация контрактов (event payload <-> usecase DTO), адаптация асинхронной модели к синхронной и обратно, нормализация ошибок/кодирования/тайм-аутов между системами, унификация idempotency/ack semantics, retry/backoff rules.
3. Bridgets — thin layer: НЕ держит бизнес-логику. Только mapping, validation of shape, error mapping, orchestration между несовместимыми API.
4. Bridgets также обязаны предоставлять интерфейс I<Module>Bridgets и фабрику New<Module>Bridgets, возвращающую интерфейс. Конкретные адаптеры — unexported.
5. Bridgets могут зависеть одновременно на двух несовместимых слоях (например на event-emitter и на usecase-интерфейсе), но должны инкапсулировать логику трансформации так, чтобы внешние слои продолжали работать с абстракциями.
6. Bridgets рекомендуется делать идемпотентными и без побочных эффектов при возможности; побочные эффекты — только через внедрённые интерфейсы (emitters, repositories).
